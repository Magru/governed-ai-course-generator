Transitions & guards

Every legal move in both machines: current state, event, the guard that permits it, the layer that evaluates the guard, and the next state — followed by the sequences that are legal, the sequences that must be refused, and the moves that do not exist at all.

A state list is an inventory; a transition table is a contract. The state model says what can exist. This page says what may happen — and, more usefully for a governed system, what may not. Half of it is written in the negative on purpose.

Section 1

How to read the table

Five columns, and the middle three are the whole point.

  • From / To — states from the state model. Remember that the course machine runs per revision: “the course” below means the revision being worked on or served.
  • Event — what arrives. Three sources, never mixed: a person, the model, or the infrastructure. Events written (auto) are the machine's own continuation once a batch of checks returns — no external actor is involved.
  • Guard — a predicate that must hold for the move to be legal. If it does not hold, the transition does not happen — not “happens and gets logged as a warning”.
  • Layer — who evaluates the guard. Every guard has exactly one owner, and no guard is evaluated twice by two tools.

Refusals are transitions too. A failed check is not an error path bolted onto a happy path — it is a row in this table with its own destination state, its own explanation, and its own next move for the editor. That is why the tables below are roughly half refusals: in a governed system that is the normal case, not the exception.

Two conventions worth stating before the tables. A guard written ¬p is the refusing branch of the same evaluation as p — one check, two destinations. And where a row's To names a different revision, the row is a spawn: the revision the row is about does not move at all.

The skeleton stays editable after content exists. OutlineRevised sends the revision back through OutlineChecks: nodes that survive keep their states and their stamps, a node removed from the skeleton is discarded with its history retained, and anything that depended on it goes stale through the ordinary cascade. This row exists because of the decision below — telling an editor to “drop the blocked node from the skeleton” is empty advice if the machine has no move for it.

A node blocked on policy stops the revision, recoverably. The row for it sends the revision to BlockedRecoverable rather than BlockedFinal, and the difference is deliberate: the policy violation is a terminal fact about that node, not about the course, and the editor has a real move — take the node out of the skeleton and carry on. Without the row the revision would sit in ContentInProgress forever, since its exit guard can never be satisfied while a blocked node exists. The stricter reading — one blocked node condemns the revision — is defensible too, and is the first open question below.

BlockedFinal and Archived have no outgoing rows. That is what terminal means here, and it is enforced by the absence of a row rather than by a check inside one.

Why the exam has no row of its own

An earlier draft gave the exam a second Planned row with its own guard, which was a mistake twice over: Planned (exam) is not a state, and two rows sharing a state and an event with guards that can both hold is exactly what Section 8 forbids. The fix is one guard that is vacuously true for a node with no topics beneath it — content_approved(topics(node)) quantifies over the empty set for a topic and over the real set for an exam. One row, no special case, and the determinism claim survives.

Three events this table had to add

Writing a transition table is the exercise that finds the events an inventory missed, so it is worth naming them rather than quietly folding them in:

  • NodeGenerationRequested — the editor picking a node and starting it. The catalogue had NodeGenerated, which is the model finishing; the two were being conflated.
  • CourseChecksRequested — the editor declaring the revision done. Without it, ReadyForReview would have to run whole-course checks the instant its guard turned true, which is both expensive and wrong: reaching the state means the machine has nothing left to object to, not that the editor has finished.
  • WithdrawRequested — pulling a live revision off air without waiting for a re-check. The state model offered “withdraw early” as an action with no event behind it.

Two of the three exist because a state can be entered automatically and still need a human to leave it. That distinction does not show up in a state list at all.

Section 4

Every guard, in full

The state model named thirteen core guards; the tables above need fourteen more to be complete. All twenty-seven, with their owner and what they produce when they refuse — because a guard that returns only false is useless to the person who has to act next.

schema_valid(artifact)
JSON Schema — the brief, the outline, or a block has the shape it must have. Refuses with the failing path and the expected type.
policy_allows(action, role, state)
OPA — may this actor take this action, over this audience, in this state? Refuses with the rule that denied and a human-readable reason. The only guard whose refusal is terminal.
guardrail_clean(artifact)
Managed guardrail — text and images carry nothing forbidden. Refuses with a category, never with a matched string. An explicit deny is a refusal; an unreachable service is a timeout, which is an unknown and routes to ErrorRecovery — the run stalls either way, but the two are not the same event and must not be recorded as one.
feasible(brief)
Z3 — the brief's requirements are mutually satisfiable, and satisfiable against the organization's thresholds. Refuses with an unsat core: the smallest set of requirements that cannot hold together.
skills_grounded(outline)
Datalog — every skill the outline claims is derivable from the organization's catalog. Refuses by naming the invented skills.
grounded(node)
Datalog — every claim in the node hangs on a retrieved chunk. Refuses by naming the unsupported claims.
no_permission_leak(scope)
Datalog — no source used anywhere in the scope is invisible to any member of the intended audience. Refuses with the path: node → source → the audience that lacks rights.
ordering_acyclic(course)
Datalog — the prerequisite graph has no cycles and agrees with lesson order. Refuses with the cycle.
objectives_covered(scope)
Prolog — every learning objective is closed by some node. Refuses with the uncovered objectives, which is also what drives the editor's next-best-action.
content_approved(topics(exam))
Datalog — an exam may not be generated before the topics it tests are approved. Refuses by naming the topics still outstanding.
depends_on(node, edited)
Datalog — the staleness cascade, evaluated as a guard rather than run as a procedure. Returns the dependency path, which becomes the reason recorded on each withdrawn approval.
trace_satisfies_ltl(course)
Temporal logic — the recorded history obeys every invariant. The only guard that reads the past rather than the present. Refuses with the violated formula and the event that broke it.
block_schemas_valid(node)
Catalog schema — every block validates against the settings schema its catalog entry names, at the catalog version stamped on the revision.
all_visuals_reviewed(node)
Catalog flag · Human — every block whose type carries requires_visual_review has been looked at by a person. Refuses with the queue of unreviewed visuals.
arithmetic_consistent(node)
Z3 — the numbers inside a node add up: exam points reach the stated maximum, durations match the block count. Refuses with the failing sum.
successor_published(revision) · blocked_at(revision)
State store — bookkeeping the pointer and the stop need: which revision took the live pointer, and which state a recoverable block was entered from, so the fix returns there instead of to the beginning.
all_nodes_approved(revision) · no_stale_nodes(revision)
State store — the two quantified conditions that lift a revision out of ContentInProgress. Refuse with the offending nodes.
retry_budget_left(scope)
State store — repair_count < repair_budget, where the budget is organizational configuration, not a constant. Refusing is what turns a repair loop into a stop.
idempotency_key_unused(operation)
State store — has this side-effecting operation already landed? Asked before any retry, which is what makes a timeout an unknown rather than a failure.
versions_current(artifact)
State store — the stamps on the artifact match the current policy, guardrail, catalog and KB versions. Refusing sends a live revision to StaleReview rather than blocking it.
is_draft_revision(revision)
State store — this revision has never been published. Guards every editing transition in both machines; it is the single point at which immutability is enforced.
differs_from_live(revision)
State store — this revision is not byte-identical to the one currently serving. Stops a fork nobody touched from being published and moving the pointer for nothing.
affected(revision) · has_active_readers(revision)
Datalog · State store — which revisions a configuration change reaches, and whether anyone is still reading a superseded one. Together they scope the staleness sweep.
approval_chain_satisfied(revision)
OPA — the signatures this organization requires for publication are present. Configuration decides how many and whose; the guard only checks.

Every guard refuses with an artifact, not a boolean. An unsat core, a dependency path, a violated formula, a named rule, a queue of unreviewed images. This is the property that makes the difference between a system that blocks and a system that can be worked with — and it is also what a repair loop consumes on its next attempt.

Section 5

Legal event chains

Four sequences the machine must accept. Each is a path through the tables above, written as the trace would record it.

1 · The shortest legal life of a course

BriefSubmitted → GuardrailVerdict(allow) → (feasible) → OutlineGenerated → GuardrailVerdict(allow) → (checks pass) → OutlineApproved → NodeGenerationRequested ×N → NodeGenerated ×N → GuardrailVerdict(allow) ×N → (checks pass) ×N → NodeApproved ×N → CourseChecksRequested → (checks pass) → ApprovalGranted → PublishRequested AwaitingBrief → … → Published, no repair, no refusal

Notice what is not optional even here: three guardrail verdicts, two batches of formal checks, and three kinds of human decision. The shortest legal path still cannot skip a layer.

2 · A repair inside the budget

NodeGenerated → GuardrailVerdict(allow) → CheckFailed(datalog, ungrounded) → [retry_budget_left ✓] → NodeGenerationRequested → NodeGenerated → GuardrailVerdict(allow) → (checks pass) → NodeApproved

Legal because retry_budget_left held at the moment of the repair. The same chain once the budget is spent is forbidden chain 8 — at a budget of two that is the third failure, and the difference between legal and forbidden is a counter, not a category.

3 · Revising a live course, and rolling it back

rev 1: Published ReviseRequested → rev 2 spawned in ContentInProgress NodeEdited(T) [is_draft_revision ✓ — on rev 2] → (cascade, checks, approvals inside rev 2) → ApprovalGranted → PublishRequested [differs_from_live ✓] → LivePointerMoved: rev 2 → Published, rev 1 → Superseded RollbackRequested(rev 1) → rev 1 → StaleReview → (re-verified against current versions, passes) → LivePointerMoved: rev 1 → Published (re-stamped), rev 2 → Superseded

The rollback is legal because it went through StaleReview. Written as a direct Superseded → Published it is forbidden chain 6, and the same two revisions end in the same two states — the difference is entirely in whether a re-verification happened on the way.

4 · A rule changes and nothing stops

PolicyChanged(v7 → v8) affected(rev A) ✓ → rev A: Published → StaleReview affected(rev B) ✗ → rev B: untouched, still Published affected(rev C) ✓ ∧ has_active_readers ✓ → rev C: Superseded → StaleReview rev A: (re-check passes) → Published, re-stamped v8 rev C: (re-check fails) → Withdrawn, readers cut over

Three revisions, one event, three different outcomes, no deployment and no downtime. This chain is the practical answer to “what happens when compliance changes its mind”, and it is legal precisely because none of it edits anything.

Three of these — 1, 6 and 11 — are refused by the absence of a row rather than by a guard evaluating to false. That is the stronger form: a guard can be misconfigured, a missing transition cannot. Where a refusal matters most, prefer to make the move unrepresentable rather than merely disallowed.

Section 7

Moves that do not exist

Worth listing separately, because each is a move a reasonable person would expect to find:

  • Published → ContentInProgress — the transition the model deliberately does not have. Revising a live course spawns a different revision; the live one never moves. On the diagram this edge is dotted for exactly that reason.
  • Superseded → Published — rollback goes through re-verification or not at all.
  • BlockedFinal → * — no admin override. A terminal state an administrator can undo is terminal in name only.
  • Validated → Published — nodes are never published; revisions are. A node reaching Validated means the formal layers are satisfied, which is not the same as anyone having agreed to it.
  • Any node transition against a published revision — is_draft_revision guards all of them, so immutability is one predicate rather than a rule repeated in seventeen rows.
  • Cloning an archived course — the state model offers it, and it is deliberately not a transition: a clone creates a new course identity with its own first revision in AwaitingBrief. Nothing about the archived revision changes, so it belongs to the layer above this machine.
  • A skip from Generated to NodeChecks — there is no path that avoids the guardrail hop, which is what makes G(generated(A) → O guardrail_checked(A)) checkable over the trace rather than merely intended.
Section 8

Totality, determinism, concurrency

One recovery state, shared by two machines

ErrorRecovery appears in both tables and is one state, parameterized by the scope of the operation that failed, not two states with the same name. The exit rule is a single sentence in both cases — check idempotency_key, then decide about a retry — and splitting it would duplicate the only interesting logic in the model, which is how such rules drift apart. The cost is that a state belongs to two machines at once, which is unusual enough to say out loud rather than leave for a reader to notice: it is counted once, in neither total.

The transition function is partial, and that is explicit

Most (state, event) pairs have no row. An event arriving where no row matches is recorded and discarded — it does not error, does not queue, and above all does not fall through to a default. A stale GuardrailVerdict arriving after the editor cancelled a run is the ordinary case for this, and the trace keeps it so that “why did nothing happen?” has an answer.

Determinism

No (state, event) pair has two rows whose guards can both hold. Where two rows share a state and an event they are complementary branches of one evaluation, so the next state is a function of the current state, the event, and the guard results — with no ordering dependence and no first-match-wins rule to remember.

Making that true costs something, and the cost is visible in the tables: the three refusal rows in BriefValidation carry the earlier checks in their guards (schema_valid ∧ ¬policy_allows, not just ¬policy_allows), and the repair rows carry policy_allows ∧ constraint violated so that a brief failing both a policy and a constraint has one destination rather than two. Ordering is then a consequence of the guards rather than a rule the reader has to hold separately — which is the point, because a rule held separately is a rule that drifts.

The guards themselves are deterministic by construction: every one is owned by a formal layer or the state store. The single non-deterministic input to the whole system — the model — is not consulted by any guard. It produces artifacts that guards judge, and that asymmetry is the reason the machine can be reasoned about at all.

Two editors, one revision

Node work is naturally partitioned — two editors on two nodes do not interact, and the course-level guard simply observes whatever the node states become. What genuinely conflicts is two editors on the same node, and the same revision-level action taken twice. Revision-level transitions are serialized per revision and node transitions per node, with idempotency_key making a repeated request a no-op rather than a second side effect.

At the interface the answer falls out of the model rather than needing a mechanism of its own: the screen follows the state machine, live. A colleague's approval is an ordinary node transition carrying who and when, so the state changes under the reader and the stamp says who changed it — the state is the notification. Nothing is locked, because “busy” is not a concept this model has; and an attempt to write over a state that has moved is a visible conflict rather than a silent overwrite, which is the one outcome a system that promises to lose nothing quietly cannot afford.

Section 9

Open questions

  1. Does a revised skeleton have to stop at OutlineReview again? The table sends OutlineRevised to OutlineChecks and leaves the question of a second human approval open. Requiring it is more control and more clicks on a change the editor just made themselves; skipping it means the skeleton can move without anyone signing the new shape.
  2. Does a live-updating approval screen need to freeze once opened? The screen follows the state machine, which is right — until the thing being approved changes while it is being read. An approval records what the approver was shown, so either the screen holds still until the decision is made, or the record has to say which version they actually saw.
