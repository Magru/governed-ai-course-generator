AI Architect · Final Project · Spec v2

Governed AI Course Generator

Second version of the specification — the answer to the design problem raised when the idea was approved. The proposal itself stands; what changes is where the boundary runs between what we build and what we configure.

Structure is ours. Meaning and modality are managed. The decision is the human's. If a check can be written as a statement about a graph, a set, an ordering, or a number — it belongs to our formal engines. If it requires understanding text or looking at an image — it is not written in code at all. If it is about pedagogical value — a person makes it.

Section 1

The problem, as we read it

The idea was approved with a challenge attached, delivered as five hints: don't solve it in code · what happens if you solve it in code and then leave the company? · what happens at deployment — do we stop everything? · a pointer at multimodality · and finally if you solve it in code, you won't finish the project in time.

In v1 we implicitly signed up to build the layer of meaning ourselves. The five formal tools can only reason about structure. Everything that requires understanding a text or seeing an image — a banned topic phrased indirectly, the safety of generated prose, the content of an illustration, the relevance of a retrieved chunk — is beyond them. Hand-writing that layer cannot be done in the project's timeframe, cannot be maintained after I leave, and cannot be changed without a release.

Two pieces of evidence, neither of them our own reasoning:

Evidence from the product

The builder's block catalog is a constant in the platform's frontend, and its own comment demands a second copy in the backend:

“Backend enforcement lives in apps/knowledge_base validators (mirror this set). When adding a new block type, decide here whether it belongs to KB.”

The platform's vocabulary is duplicated across two places in code. Adding a modality — video, audio, SCORM, an interactive block — requires a developer and a deployment. That is hints 1 through 4, stated by the product itself.

Evidence from the course

The Tool Safety lecture lists four anti-patterns of bad guardrails. The first is “keyword filter only” — trivially bypassed by rephrasing, encoding, or a chain of individually innocent steps. Validating banned topics with OPA over strings, as v1 proposed, is exactly that anti-pattern.

The same lecture: a valid schema is not a valid policy, and policy must live as an external, versioned layer that can be updated without touching either the code or the model.

Section 3

Three layers of responsibility

Formal engines

Our code and rules

OPA · Z3 · Prolog · Datalog · LTL. Everything structural: rights, ordering, dependencies, staleness, arithmetic, objective coverage.

“A restricted chunk must not reach a broad-audience course” — that is a graph of relations, not a meaning.
Managed services

Configuration, not code

Guardrails · Knowledge Bases. Everything semantic and perceptual: banned topics in free text, harmful content, PII, what is inside an image, whether a retrieved chunk is relevant.

“The author asks for something forbidden, phrased indirectly” — that is meaning, not structure.
The human

Judgment and publication

Pedagogy, quality, publishing. Skeleton approval, per-node approval, final publish approval.

Delegated to no model, no service, and no logic.

The three layers are not a hierarchy but a division of competence. Each answers a question the other two cannot: is this permitted and consistent (formal), does this mean something harmful (managed), is this worth teaching (human).

Section 4

The Generation Gateway

Structurally this is the Tool Gateway from the Tool Safety lecture, applied to generation: a membrane between the LLM and the system that every call must cross. The model proposes; the gateway decides; the tool — here, the act of writing into course state — runs only if allowed.

Why the guardrail is an explicit hop

Sylla production calls Claude through the Anthropic SDK on Bedrock, not through the bedrock-runtime client. A guardrail therefore cannot be a checkbox wrapped invisibly around the model call — it is an explicit ApplyGuardrail request, an API deliberately built to be model-independent: it evaluates text and images without invoking any model.

That constraint turns out to be an advantage. The guardrail becomes a visible step of the architecture — present in the state machine, in the trace, and on the defense diagram; its verdict is recorded in the audit log and fed to the formal layer as a fact; and when the service is unavailable the gateway fails closed, exactly as the lecture demands of a policy gate.

Section 6

The five formal tools after the handoff

Moving semantics outward does not weaken a single one of them. Each keeps an irreplaceable structural job, and each now has a place where a managed verdict enters as a fact.

Section 7

Permissions and leaks — v1's strongest part, preserved

The real Sylla model: a KB category binds to access-control teams, individual members can be granted access directly, and a denormalized closure records every effective category-to-team pair (a category's own teams plus its ancestors'). An empty closure means the chain is public.

  1. At retrieval time: the course audience's rights are expanded into a metadata filter on the query, so the service physically cannot return what the audience may not see.
  2. After retrieval: Datalog re-checks every returned chunk ID against the same closure — exposed_to_restricted(Course) :- grounded_in(Node, Chunk), restricted(Chunk), audience_lacks(Course, Chunk).

Why both and not one: the filter is a service configuration, which can be wrong, over metadata that can be stale. The managed layer makes retrieval fast and clean; the formal layer is what proves the result. This is defense in depth, and it is the clearest slide in the deck: speed from configuration, guarantees from logic.

Section 8

Vocabulary as data

The answer to the multimodality hint and to "what if you leave the company".

  • The generator keeps no copy of the catalog. The platform is the source of truth: block type, the JSON schema of its settings, its modality (text / image / video / audio / interactive / document), and its applicability policy.
  • The node pipeline is modality-agnostic by construction: it does not know about "text and images", it knows about "blocks, each with a modality and a schema". There is no branch per modality to rewrite.
  • A new modality arrives as a catalog entry: the generator can immediately propose it (its schema goes into the forced tool call), the guardrail can moderate it, Datalog can trace its provenance, OPA can restrict it. Zero lines of code, zero deployments.
  • The same logic covers the rest of the vocabulary — the skills catalog, KB categories and their rights, thresholds such as "a quiz needs at least N questions", the model routing table. These are organizational data that belong where the skills catalog already lives, not constants inside our release.

This also repairs something the platform already suffers from: today the catalog exists twice, in the frontend constant and in the backend validators that must mirror it. A single governed source removes the duplication rather than adding a third copy.

Section 9

Policy versioning — the answer to “do we stop everything?”

Managed configuration answers half the hint: a rule changes without an application release. The other half is what happens to courses that were already approved under the old rule. The answer reuses machinery the design already has.

A policy change is an event in the system, not a release
flowchart LR
  PC["Compliance officer edits the policy — configuration, no deploy"] --> V["New policy version"]
  V --> DQ["Datalog: which approved artifacts were stamped with the old version?"]
  DQ --> ST["Affected nodes and courses marked NeedsRevalidation"]
  DQ --> UN["Unaffected courses keep running untouched"]
  ST --> RC["Re-check through the same gateway"]
  RC --> OK["Re-approved, new version stamped"]
  RC --> BL["Now violating — blocked with the diff explained"]

  classDef default fill:#FFFFFF,stroke:#8B958F,color:#202A35;
  classDef blocked fill:#F4E7DD,stroke:#A6512B,color:#5C2D16;
  classDef terminal fill:#E3EFEA,stroke:#0E6E5C,color:#0B4438;
  class ST,BL blocked;
  class OK,UN terminal;
  • Every approved artifact is stamped with the versions it was approved under: policy bundle, guardrail, block catalog, model and version, KB snapshot.
  • When a rule changes, nothing stops. Datalog finds the dependent artifacts and marks them NeedsRevalidation — the same cascade that already handles an edited node.
  • The editor sees a re-validation queue; a course cannot remain published in violation of the current rule.
G(published(C) → policy_version(C) = current ∨ marked_stale(C))

Stated for the defense: changing a rule is an event inside the system, not a deployment. Nothing is halted; exactly the courses the rule touches go back for re-validation, each with an explanation of what changed.

Section 10

The objection this invites

“Managed moderation is your own anti-pattern — asking a model whether something is safe.”

  1. It is not the same model. The judgment comes from a separate system, not from the model that produced the content — there is no self-confirmation loop.
  2. Its configuration is external and versioned. Denied topics and filter thresholds live outside the prompt and outside the code — precisely what the lecture requires of policy.
  3. The verdict is an input, not a decision. The guardrail never publishes and never moves a state; its answer becomes a fact for OPA, for the proof tree, and for the audit log. The model retains zero authority over transitions.
  4. It fails closed. If the service is unavailable, generated content is not admitted into course state.

And symmetrically — what the managed layer does not do, which is a slide of its own: it knows nothing about pedagogy, does not check objective coverage, cannot see dependencies between nodes, does not understand the organization's permission model, and does not track ordering over time. All of that stays with the formal engines. Drawing that boundary honestly is the architectural contribution.

Section 11

Demo — four steps added to the editor's journey

The eleven steps of v1 remain. Four are added, each demonstrating one hint answered.

  1. BlockBypassing the string filter. The author phrases a forbidden topic indirectly. A string-matching policy would pass it; the guardrail blocks at the entrance and the model is never called.
  2. BlockAn unsafe illustration. A generated image fails the multimodal content filter and never reaches the editor — the modality that neither code nor logic can inspect.
  3. StaleA policy change after approval. A compliance officer adds a denied topic in configuration, with no deployment. Datalog cascades the mark to the approved courses it touches; LTL catches the attempt to remain published under the old version.
  4. PassA new modality for zero code. A block type is added to the catalog; the generator immediately proposes it, its schema validates, its provenance traces — nothing is rebuilt and nothing is redeployed.
Section 12

Risks, limits, reproducibility

RiskResponse
Vendor dependencyModeration and retrieval sit behind ports; the implementation is replaceable. Sylla production already runs on the same cloud, so this is not a new dependency.
The guardrail knows no pedagogyNor should it — that is the work of Prolog, Datalog, and the human. The boundary is stated explicitly rather than blurred.
Latency and cost of extra hopsHops occur only at generation boundaries; a light model handles cheap tasks, and verdicts are cached by content hash.
False positives on legitimate training contentThresholds and denied topics are configured by the organization; every block arrives with a reason and enters the repair loop rather than a dead end.
“Too much was handed outward — where is the contribution?”The contribution is formal guarantees, permissions, staleness, versioning, and vocabulary-as-data. The managed layer covers only what cannot be written in code at all.
The managed layer is unavailableFail-closed plus a kill switch: generation is disabled, the course stays in its current state, nothing is published.

Reproducibility

The record/replay cassettes now capture more than model responses: every guardrail verdict (allow or blocked, with its reason, for text and for images) and every retrieval result (chunk IDs plus metadata) is recorded as a fixture. Without that, the offline verification promise of v1 would quietly break.

Open questions

1. Is the problem read correctly — that semantics and modalities should be configured through managed services rather than written in code, leaving our code the formal core and the glue between layers?
2. Still open from the proposal: the code submission date (is 4 October the defense only?), solo or group work, and the submission channel.
3. How deep should the live integration go in the prototype — real service calls, or an adapter over recorded cassettes?
