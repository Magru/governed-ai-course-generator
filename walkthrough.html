One course, end to end

Twenty-four steps from an empty brief to a published course: every state change, every check, every stop — in the order they actually happen.

First how it drives, then how it breaks. The state model inventories what exists and, in its nine situations, what goes wrong. This page does the other half: a single run that succeeds, followed step by step — because the order of the layers is the design.

Section 1

The run

One editor, one course, no adversary. Everything below is the ordinary case — the interesting part is how much structure the ordinary case already needs.

course Incident Response for Support Engineers audience support-team nodes T1 Detection · T2 Triage · T3 Escalation · E1 Exam sources the organization's Knowledge Base, already filtered to what support-team is allowed to see

Three actors appear in the margin of every step, and they are never interchangeable: automatic a deterministic layer or a guard, model a generation call, editor a person deciding something no layer can decide.

Section 2 · Act I

The brief — three refusals before the first token

Nothing here costs a cent. That is the point: every refusal the system can make cheaply, it makes before the model is ever called.

  1. The course is created editor

    A course row exists and nothing else — an identifier and an owner. No brief, no nodes, no history.

    course: AwaitingBrief

  2. The brief is submitted automatic

    Three checks run in order, cheapest first: the JSON schema of the brief (shape), OPA (may this editor author for support-team, is the request inside the organization's limits), and the guardrail (topic and personal data in the brief text itself).

    course: AwaitingBrief → BriefValidation writes: policy_version=v7 · guardrail_version=g3 · verdict + reason on failure: → BlockedFinal, permanently

    If it fails here the trace carries no model_id and no token count, because there was no model call. A policy refusal that costs nothing is the cheapest kind of safety there is.

  3. The brief is checked for feasibility automatic

    Z3 pre-flight: “forty lessons, two hours total, fifteen minutes each” is unsatisfiable arithmetic, and it is unsatisfiable before anything is generated.

    course: BriefValidation → BriefFeasibility sat → on to generation unsat → BlockedRecoverable + the unsat core: the exact requirements that cannot hold together

Two refusals, two different words. A policy violation is terminal; an arithmetic contradiction is the editor's to fix. Calling both of them “blocked” would be a lie told to the person who has to act next.

Section 3 · Act II

The skeleton — the first meeting with the model

The model proposes a structure. Four layers decide whether that structure is allowed to exist, and one of them sends it back once.

  1. The outline is drafted model

    Retrieval runs over the Knowledge Base already narrowed by rights, and the model is called with a forced JSON schema. What comes back is a structure — topics, objectives, prerequisites — not prose.

    course: BriefFeasibility → OutlineDrafting writes: idempotency_key · model_id · kb_snapshot

  2. The outline passes the guardrail automatic

    A separate hop, and therefore a separate state. Not because “a check deserves a state”, but because this is a network call the editor may close the laptop in the middle of, and recovery must know the run was inside one.

    course: OutlineDrafting → OutlineGuardrail → OutlineChecks

  3. Four formal layers examine it automatic

    schema the outline has the shape a course must have Datalog every claimed skill is derivable from the catalog — not invented OPA the structure obeys the organization's rules Z3 the counters add up: duration, node count, objective spread

    Say Datalog objects: the model wrote post-mortem facilitation, and no such skill exists.

  4. The outline is repaired, once automatic model

    course: OutlineChecks → OutlineRepair → OutlineDrafting course.repair_count: 0 → 1 the prompt now carries the explanation, not just "try again"

    The second pass is clean. The distinction matters: a retry repeats a request, a repair changes it — the failure is fed back as a specific, machine-produced reason.

  5. The editor reviews the skeleton editor

    First kind of stop. The screen shows three topics and an exam, plus what was repaired and why. The editor renames two topics, deletes a fourth, and approves.

    course: OutlineChecks → OutlineReview

  6. Nodes come into existence automatic

    course: OutlineReview → ContentInProgress T1, T2, T3, E1: Planned

    Not one node could have existed before this moment. That is not a UI convention — it is the invariant G(content_generated(N) → O outline_approved), checked over the trace at the end.

Section 4 · Act III

The nodes — the cycle that repeats

From here the node FSM runs, and it runs per node: T1 can sit approved while T3 is still being repaired. Nothing about one node's trouble touches another.

  1. T1 is drafted model

    Retrieval is now narrowed to this topic rather than the whole course, and the model assembles blocks against the schemas in the catalog — text, example, image, quiz.

    T1: Planned → ContentDrafting writes: idempotency_key for this operation

  2. Its output passes the guardrail automatic

    Text and images, in one call, with no model invoked to do it.

    T1: ContentDrafting → Generated → OutputGuardrail

  3. Four questions are asked of the content automatic

    schemas every block validates against its catalog schema grounding every claim hangs on a chunk id (Datalog) rights those chunk ids are ones support-team may see coverage the node closes its own learning objectives (Prolog)

    The third one is the quiet one. A node can be perfectly accurate and still be a leak, because the source it quoted belongs to a team the audience is not in.

  4. T1 is formally clean automatic

    T1: NodeChecks → Validated

    Validated means every layer that can produce a proof has produced one. It does not mean the node is good.

  5. The editor approves T1 editor

    Second kind of stop. One block in T1 is an illustration, and the catalog marks that block type requires_visual_review — so the node cannot leave Validated until a person has actually looked at the picture. The approval screen shows two things: the formal verdict, and the queue of visuals waiting for an eye.

    T1: Validated → NodeApproved stamped: policy_version · guardrail_version · catalog_version model_id + version · kb_snapshot appended: approvals[] — who, when, and what they were shown

    An approval is not a boolean. It is a set of stamps that says approved against these named versions — and that is what makes step 24 and everything after it possible.

  6. T2 runs the same cycle model automatic editor

    T2: Planned → … → NodeApproved (clean on the first pass)

  7. T3 times out automatic

    The provider does not answer. This is not a failure — it is an unknown, and the two are handled differently.

    T3: ContentDrafting → ErrorRecovery first action: check idempotency_key the write landed → move on, do not regenerate it did not → one bounded retry the editor is not told anything yet

  8. T3 completes and is approved editor

    T3: → NodeChecks → Validated → NodeApproved
Section 5 · Act IV

The exam — a node with a precondition

Every node so far could have been generated in any order. The exam could not.

  1. The exam waits on its topics automatic

    E1 has been Planned since step 9, but its generation is fenced: an exam may not be written before the topics it examines are approved. The button is not merely greyed out — the transition does not exist.

    guard: content_approved(topics(E1)) invariant: G(exam_generated(E) → O content_approved(topics(E)))

  2. The exam is drafted and checked model automatic

    The same cycle as any node, plus two checks only an exam needs.

    Z3 the points per question sum to the stated maximum Datalog every question traces to an approved topic — not to the Knowledge Base at large

  3. The exam is approved editor

    E1: Validated → NodeApproved T1, T2, T3, E1: all at rest
Section 6 · Act V

The course as a whole

Node-level checks cannot see the course. These four can.

  1. The course becomes ready by itself automatic

    Nobody pressed “done”. A guard over the node states became true, and the course state followed. This is what it means for the course FSM to be derived rather than driven.

    guard: all_nodes_approved(C) ∧ no_stale_nodes(C) course: ContentInProgress → ReadyForReview

  2. The whole course is checked automatic

    completeness every objective in the brief is covered by some node ordering the prerequisite graph is acyclic and agrees with lesson order rights no chunk anywhere in the course leaks past the audience temporal the trace itself is replayed against the invariants

    The last line is the one that has no equivalent at node level: it checks history, not current state. Did the exam really come after its topics were approved? Did every generated artifact really pass a guardrail? A system can be in a perfect state and still have got there illegally.

  3. A person takes responsibility editor

    Third kind of stop, and the only one that is about accountability rather than content.

    course: WholeCourseChecks → PendingApproval → Approved the course is stamped as a whole, the same way each node was

  4. The course is published editor

    course: Approved → Published
Section 7 · Act VI

After publication — where a pipeline would have ended

Step 24 published revision 1, and revision 1 will never change again. Three things still reach into a live course, and none of them edits it: the machinery is the version stamps written at every approval, the dependency graph, and a fork.

A published revision is immutable. There is no transition out of Published that touches content. A learner who opens a lesson is reading exactly the bytes a person approved, under versions that are still on record — for as long as that revision is live, and afterwards too.

The editor fixes a sentence in an approved topic

Not an edit of the live course — a fork. Every node is copied with its state and its stamps, so the new revision starts with everything approved and nothing stale, and the editor works where no learner can see.

ReviseRequested rev 2 created: ContentInProgress rev 1: unchanged, still Published, still live NodeEdited(T2) in rev 2 T2: NodeApproved → NeedsRevalidation E1 and T2's images follow — in rev 2 only reason: dependency changed → T2

Nobody wrote that cascade. The exam is stale because it was traced to T2 when it was written; the image is stale because its prompt came from T2's content. It is the same dependency graph that hunts permission leaks, used for a second purpose — and now it only ever fires inside a draft.

The revision goes live, and the old one survives

guard: differs_from_live(rev 2) ∧ all_nodes_approved ∧ no_stale rev 2: → ReadyForReview → WholeCourseChecks → Approved → Published live pointer: rev 1 → rev 2 rev 1: → Superseded intact, still stamped, still readable rollback = move the pointer back to rev 1 nothing regenerated, nothing restored from a backup

That last line is the whole return on the decision. Rollback — which the brief asks for under production readiness — stops being a recovery procedure and becomes a pointer move to something that was never damaged.

A compliance officer changes a policy

PolicyChanged(v7 → v8) revisions stamped policy_version=v7 AND touched by the new rule → StaleReview every other revision: untouched, still Published re-judged against v8 — no content is regenerated passes → back to Published, re-stamped v8 fails → Withdrawn, and the fix is a new revision

This is what the stamps are for. Without them, the honest answer to “which published courses does this new rule affect?” is “all of them”, and the only safe action is to stop everything. And note what the re-check cannot do: it cannot quietly amend the course to make it comply. A live revision either passes under the new rule or stops being served.

The Knowledge Base is updated

Identical mechanism, different stamp: nodes grounded against a kb_snapshot whose chunks have changed are flagged, because grounding was a claim about a specific state of the sources — not about the sources in general. As above, the flag routes to re-verification, and any repair happens in a fork.

Section 9

What only an end-to-end run shows

  1. The three human stops are three different questions. The skeleton stop asks “is this the right course?”, the node stops ask “is this the right content?”, the publication stop asks “am I willing to sign this?”. None of them is a confirmation dialog, and none could be merged into another without losing the question it asks.
  2. Money is spent at step 4, and steps 1–3 are already complete refusals. The ordering of the layers is economic as much as it is logical: schema before policy, policy before arithmetic, all of them before the model. A system that calls the model first and validates afterwards pays for every rejection.
  3. The course state is never set by hand. Every course-level transition in this run except three approvals and the publish click was derived from node states by a guard. That is the difference between a state machine and a status field.
  4. Two failures in the run were handled without telling anyone. The outline repair and the timeout both resolved inside the machine. Bounded automatic recovery is what earns the right to interrupt a human when something genuinely needs them — an agent that escalates everything trains its editor to approve everything.
