State inventory

The two-level state machine behind the generator: what actually persists between editor sessions, where the process is allowed to stall, and which invariants must hold over the whole trace.

A check is not a state — a stall is. We do not mint a state per validation. We mint one wherever the process can stop and wait: for a human, for a retry, for a decision. Everything else is a step inside a transition.

Section 1

How these states were derived

  1. A state is what survives the editor closing the laptop. If something need not be restored after three days away, it is a variable inside a step — not a state.
  2. Two levels. The course is long-lived and aggregates its nodes; each node runs its own cycle. Course-level guards quantify over node states rather than duplicating them.
  3. A check is not a state; a stall is. States exist where the process waits — on a human, on a retry budget, on a decision, or on an external call whose outcome must survive a crash. That last clause is why the guardrail hops and the check batches appear as states at all: they are network hops, the editor may close the laptop in the middle of one, and recovery has to know the run was inside a call before it can decide whether retrying is safe.
  4. Two classes of blocking. A policy violation is terminal (BlockedFinal); a constraint or grounding violation is recoverable — it enters a bounded repair loop and, if the budget runs out, lands in BlockedRecoverable.
  5. Modality creates no states. An image is a block with a modality, not a branch of the machine. "A human must sign off on the visual" is a flag on the block type, carried by the catalog — not a state of the course.
  6. Every state answers three questions for the editor: what is available now, what is blocked and why, and what to do next. The wizard is this machine, rendered.

Where a course starts and where it ends

Initial: AwaitingBrief — the only state a course can be created in. Terminal: Archived (withdrawn, kept for audit) and BlockedFinal (a policy violation, read-only from then on). Quasi-terminal: Published — a course rests here indefinitely and leaves only by being archived, or by a change that sends it to StaleReview. Every other state is transient by design: it either advances, repairs, or waits on a person.

Why ErrorRecovery is not just "retry"

Generating a node is an operation with side effects: it writes into course state and spends money. So the exit from this state is not "send the request again" — it is: check the idempotency_key, find out whether the operation actually completed, and only then retry with backoff. A timeout is an unknown, never a failure.

Blocks that need a human eye

Some block types cannot be cleared by any check — an illustration is the obvious one. The catalog marks those types requires_visual_review, so the requirement travels with the vocabulary rather than being hard-coded per modality: whoever adds a new visual block type declares it there, and the machine inherits the rule.

The flag is carried on the block, and it gates the node: a node reaches Validated when the formal layers are satisfied, but it cannot reach NodeApproved while any flagged block is still unseen. The editor's approval screen therefore shows two things — the formal verdict for the node, and the individual visuals still awaiting an eye. Rejecting one visual does not discard the node: that block returns to NodeRepair with the editor's reason, and everything already cleared stays cleared.

Initial: Planned — every node is born from the approved skeleton. Terminal: BlockedFinal. Resting: NodeApproved — the state a node is supposed to end in, which it leaves only when it or a dependency changes. A course is publishable exactly when every node rests there.

Section 4

The staleness cascade

This is the centerpiece of the design, and the reason the machine is two-level rather than one long pipeline.

Editing an approved node moves it to NeedsRevalidation — and Datalog marks the same status on everything that depends on it: the exam that tests this topic, the illustrations derived from this lesson's content, the nodes whose prerequisites point at it. A course cannot reach ReadyForReview while a single stale node remains, and a published course carrying one lands in StaleReview rather than quietly serving contradictory material.

The same machinery answers a second question, added in v2: when an organizational policy changes, the artifacts stamped with the old version are found and marked exactly the same way. A rule change is an event inside the system, not a redeployment.

Guards

policy_allows(action, role, state) guardrail_clean(artifact) feasible(brief) — Z3 sat grounded(node) no_permission_leak(course) all_nodes_approved(course) no_stale_nodes(course) retry_budget_left(node) versions_current(artifact) idempotency_key_unused(operation) objectives_covered(course)

Each guard belongs to exactly one layer — OPA for permission and policy, Z3 for arithmetic and satisfiability, Datalog for grounding, dependencies, and leaks, Prolog for coverage and explanation. No guard is evaluated twice by two different tools.

Section 8

What each artifact carries

Every course and every node persists more than its state name:

  • state — where it is in its machine;
  • policy_version, guardrail_version, catalog_version — what it was judged against;
  • model_id + version — who generated it;
  • kb_snapshot — which knowledge it was grounded in;
  • idempotency_key of the last side-effecting operation;
  • trace_id — the thread that ties every event together across sessions;
  • approvals[] — who approved what, when, and what they were shown at the time.

Those fields are what make two things possible at once: resuming an editor's session three days later, and answering "which approved courses does this new rule affect?" without stopping the system.

Section 9

Open questions in this draft

  1. Is editing a published course a mutation or a new edition? With learners already partway through, silently swapping content is not acceptable. One option: Published becomes immutable, an edit spawns Draft(v+1) alongside it, and publication flips a pointer — which adds a SupersededPublished state and a learner-migration question.
  2. What happens to learners mid-course when it enters StaleReview — do they continue on the version they started, or is progress frozen?
  3. Does the editor need a Sandbox for experiments that should not appear in the audit log as publication attempts?
  4. Is BlockedFinal truly terminal, or may an organization admin unblock with a justification — making that its own audited event?
  5. How granular is the cascade? If one topic out of five changes, does the whole exam go stale, or only the questions traced to that topic?
  6. Who owns retry ≤ 2 — is it a global rule or an organizational parameter? By the spec's own principle, if organizations may tune it, it is data, not a constant.
