State inventory

The two-level state machine behind the generator: what actually persists between editor sessions, where the process is allowed to stall, and which invariants must hold over the whole trace.

A check is not a state — a stall is. We do not mint a state per validation. We mint one wherever the process can stop and wait: for a human, for a retry, for a decision. Everything else is a step inside a transition.

Section 1

How these states were derived

  1. A state is what survives the editor closing the laptop. If something need not be restored after three days away, it is a variable inside a step — not a state.
  2. Two levels. The course is long-lived and aggregates its nodes; each node runs its own cycle. Course-level guards quantify over node states rather than duplicating them.
  3. A check is not a state; a stall is. States exist where the process waits — on a human, on a retry budget, on a decision, or on an external call whose outcome must survive a crash. That last clause is why the guardrail hops and the check batches appear as states at all: they are network hops, the editor may close the laptop in the middle of one, and recovery has to know the run was inside a call before it can decide whether retrying is safe.
  4. Two classes of blocking. A policy violation is terminal (BlockedFinal); a constraint or grounding violation is recoverable — it enters a bounded repair loop and, if the budget runs out, lands in BlockedRecoverable.
  5. Modality creates no states. An image is a block with a modality, not a branch of the machine. "A human must sign off on the visual" is a flag on the block type, carried by the catalog — not a state of the course.
  6. Every state answers three questions for the editor: what is available now, what is blocked and why, and what to do next. The wizard is this machine, rendered.

Where a course starts and where it ends

One clarification first, because it decides how the rest of this section reads: this machine runs per revision, not per course. A course is an identity that owns an ordered list of revisions; every state named above describes one revision. Where this page says “the course” without qualification, it means the revision currently being worked on or served.

Initial — there are two. AwaitingBrief is where a course's first revision is created, and the only way to start from nothing. ContentInProgress is where every later revision is born: ReviseRequested forks it with its predecessor's nodes already approved, so there is no brief to validate and no skeleton to draft. A machine with two entry points is worth stating outright rather than leaving the reader to infer it from a fork arrow.

Terminal: Archived (deliberately retired) and BlockedFinal (a policy violation, read-only from then on). Quasi-terminal: Published, Superseded and Withdrawn — a revision rests in any of them indefinitely; the first two each have a way back into service, and all three reach Archived eventually — Published only by way of one of the other two, since a live revision is never archived directly. Every remaining state is transient by design: it either advances, repairs, or waits on a person.

A published course is immutable

This is the decision the rest of the model hangs on, so it is worth stating flatly: once a revision is published, nothing in it ever changes. There is no transition out of Published that edits content — not for an editor fixing a typo, not for a policy change, not for the staleness cascade. A learner who opens a lesson is reading exactly the bytes a human approved, under versions that are still recorded.

What the learner is told. Not “a new version exists” — that is noise for anyone whose progress is already past the change. The dependency graph knows which nodes a revision changed and the learner's progress knows where they are, so the notice fires only where the two intersect: something you have not reached yet has changed, and you have until this date on this version. A learner past every change is told nothing, and that silence is honest rather than accidental.

What everyone calls “editing a published course” is therefore a different operation: ReviseRequested forks a new revision beside the live one. Every node is copied with its state and its stamps, so the fork begins with everything approved and nothing stale; the editor then works on the fork, and the machinery already described — edits, the cascade, checks, repair, approval — runs on a draft that no learner can see. When the fork is approved and published, the live pointer moves to it and the previous revision becomes Superseded.

a course is an identity plus an ordered list of revisions at most one revision holds the live pointer at a time rev 1 Published ──ReviseRequested──▶ rev 2 ContentInProgress rev 1 Superseded ◀──pointer moves─── rev 2 Published rollback = move the pointer back, after re-verifying rev 1 against today's versions. Nothing is ever regenerated: rev 1 was never modified and still carries the stamps it was cleared under.

A draft revision is also the answer to “where does an editor experiment?” — it is invisible to learners, it can be abandoned, and differs_from_live stops an untouched one from being published. No separate sandbox state is needed, and one would sit badly beside the rule that every action is audited.

Three consequences, and none of them cost a new mechanism:

  • The node FSM does not change at all. The same ten states, the same cascade — they simply never run against live content any more. That is the strongest argument for the decision: it removes a class of problem rather than adding machinery.
  • Node approvals are inherited; the publication signature never is. The fork copies node approvals so unchanged work is not re-reviewed — but every revision passes PendingApproval on its own. “Was this node reviewed?” and “am I willing to sign what goes live today, under today's rules?” are different questions, and only the first is about the content.
  • Rollback becomes expressible at all, which is what the brief asks for under production readiness. It is a pointer move to a revision that still exists, still holds its approvals, and still carries the versions it was cleared under — not a regeneration and not a restore from backup. It is not a free move, though: the returning revision is re-verified first, for the reason given below.
  • One guard has to be added: differs_from_live(revision). A fork that has not been edited is byte-identical to what is already serving, and publishing it would be a no-op that nonetheless moves the pointer and rewrites history. The guard keeps such a revision out of ReadyForReview.

StaleReview changes meaning accordingly. It can no longer mean “opened for editing”, because a published revision cannot be edited. It means being re-judged against the current versions, with exactly two outcomes: the revision still complies and returns to Published re-stamped, or it does not and moves to Withdrawn. Fixing it is a revision like any other.

Rolling back is a re-verification, not a bypass

“Move the pointer back” is easy to say and easy to get wrong, so it is worth being exact about what happens to both revisions. Rollback is an explicit human event — RollbackRequested, carrying a reason and landing in the audit like every other decision — and it does not put the old revision straight back on air:

RollbackRequested(rev 1) rev 1: Superseded → StaleReview rev 2: still Published, still live — nothing moved yet re-judged against today's policy, guardrail, catalog and KB versions passes → rev 1: → Published, re-stamped rev 2: → Superseded LivePointerMoved fails → rev 1: → Withdrawn, with what changed named rev 2: unaffected, still live — you cannot roll back to it

The reason for the detour is the same fail-closed instinct that governs the gateway. Revision 1 was cleared under the versions of the day it was approved; the day you want it back may be a different world. A rollback that skipped the check would be the one path in the system through which content nobody re-approved could reach an audience — and it would be the path people reach for precisely when something has already gone wrong.

Two consequences follow. Superseded is quasi-terminal rather than terminal — a mirror of Published: one guarded way back into service, plus the sweep that can pull it in while readers remain, plus retirement. And StaleReview earns its second entry point: it is the state a revision sits in whenever its right to be live is in question, whether the question came from a policy change or from a person asking for yesterday's version back.

Why ErrorRecovery is not just "retry"

Generating a node is an operation with side effects: it writes into course state and spends money. So the exit from this state is not "send the request again" — it is: check the idempotency_key, find out whether the operation actually completed, and only then retry with backoff. A timeout is an unknown, never a failure.

Blocks that need a human eye

Some block types cannot be cleared by any check — an illustration is the obvious one. The catalog marks those types requires_visual_review, so the requirement travels with the vocabulary rather than being hard-coded per modality: whoever adds a new visual block type declares it there, and the machine inherits the rule.

The flag is carried on the block, and it gates the node: a node reaches Validated when the formal layers are satisfied, but it cannot reach NodeApproved while any flagged block is still unseen. The editor's approval screen therefore shows two things — the formal verdict for the node, and the individual visuals still awaiting an eye. Rejecting one visual does not discard the node: that block returns to NodeRepair with the editor's reason, and everything already cleared stays cleared.

Initial: Planned — every node is born from the approved skeleton. Terminal: BlockedFinal. Resting: NodeApproved — the state a node is supposed to end in, which it leaves only when it or a dependency changes. A course is publishable exactly when every node rests there.

Section 4

The staleness cascade

This is the centerpiece of the design, and the reason the machine is two-level rather than one long pipeline.

Editing an approved node moves it to NeedsRevalidation — and Datalog marks the same status on everything that depends on it: the exam questions that test this topic, the illustrations derived from this lesson's content, the nodes whose prerequisites point at it. The cascade is as narrow as the dependency data allows: because every exam question is already traced to an approved topic, editing one topic out of five stales that topic's questions, not the whole exam. A course cannot reach ReadyForReview while a single stale node remains.

Because a published revision is immutable, this cascade never runs against live content: it runs inside a draft revision, where the only person who can see a half-repaired course is the editor repairing it. What reaches a published revision is the narrower question — is it still compliant under the new versions? — and that is StaleReview, which ends either in a re-stamp or in withdrawal, never in a silent rewrite.

The sweep follows the readers, not the pointer. A superseded revision is still being read by whoever started on it, so a policy change has to reach it too — otherwise the kill mechanism stops exactly where content is still being consumed. Revisions with no active readers are re-verified lazily, when someone asks for them back; revisions with active readers are swept alongside the live one.

That could grow without limit — a course revised ten times could be re-verifying ten revisions on every policy change — so the tail is bounded by time rather than left open: a learner keeps the revision they started for reader_grace_days, and after that they are moved to the current one. The window is organizational configuration, which means the cost of the sweep is a number an organization chooses rather than a property of the design. A revision past its window has no readers by definition, and drops out of the sweep on its own.

The same machinery answers a second question, added in v2: when an organizational policy changes, the artifacts stamped with the old version are found and marked exactly the same way. A rule change is an event inside the system, not a redeployment.

Four of these are worth following event by event, because they are where the design earns its keep.

A bounded repair, from failure to approval

The node is generated, the guardrail is content, but a claim in it has no source behind it.

t0 NodeGenerated node: ContentDrafting → Generated t1 GuardrailVerdict(allow) node: Generated → OutputGuardrail → NodeChecks t2 CheckFailed(datalog, node: NodeChecks → NodeRepair ungrounded: claim #3) node.repair_count: 0 → 1 t3 NodeGenerated node: ContentDrafting → Generated (prompt now carries the explanation from t2) t4 GuardrailVerdict(allow) node: → NodeChecks → Validated t5 NodeApproved (editor) node: Validated → NodeApproved node.policy_version, guardrail_version, catalog_version, model_id: stamped

What matters here is t2: the failure is not a retry signal, it is a specific explanation that becomes part of the next prompt. And t5: approval is not a boolean but a set of stamps — the node is approved against named versions, which is what makes the next situation possible.

The staleness cascade

Everything is approved, the course is one click from review — and the editor fixes a sentence in an approved topic.

before course: ReadyForReview topic T: NodeApproved exam E: NodeApproved image I: NodeApproved t0 NodeEdited(T) T: NodeApproved → NeedsRevalidation t1 (dependency graph) E: NodeApproved → NeedsRevalidation I: NodeApproved → NeedsRevalidation reason: "dependency changed → T" t2 (course guard re-evaluates) course: ReadyForReview → ContentInProgress after the course is un-publishable until T, E and I pass NodeChecks again

Nobody decided this cascade — it is derived. The exam is stale because it was traced to T when it was written; the image is stale because its prompt came from T's content. That is the same dependency graph that finds permission leaks, used for a second purpose.

A rule changes under a live course

A compliance officer adds a forbidden topic. Nothing is deployed, nothing stops, and — because published revisions are immutable — nothing is rewritten.

t0 PolicyChanged(v7 → v8) no revision changes state yet t1 (dependency graph) revisions stamped policy_version=v7 AND touching the new topic → StaleReview every other revision: untouched, still Published t2 re-check through the gateway — no content is regenerated, the existing revision is re-judged against v8 passes → back to Published, re-stamped v8 fails → Withdrawn, with the diff explained and the revision pulled from its audience t3 (only if it failed) ReviseRequested → rev n+1 forks and the repair happens there

This is what the version stamps are for. Without them the only honest answer to “which published courses does this new rule affect?” would be “all of them”, and the only safe action would be to stop everything. Note what t2 does not do: it does not edit the course to make it comply. A published revision either passes under the new rule or stops being served — repair is always a new edition.

An editor changes a course that is already live

The same edit as the cascade above, but after publication — and the difference is the entire point of the decision.

before rev 1: Published (live pointer) learners reading it t0 ReviseRequested rev 2 created: ContentInProgress every node copied with state + stamps rev 1: unchanged, still Published, still live t1 NodeEdited(T) in rev 2 T: NodeApproved → NeedsRevalidation E, I follow — inside rev 2 only t2 … checks, repair, approvals inside rev 2 … t3 guard: differs_from_live(rev 2) ∧ all_nodes_approved ∧ no_stale rev 2: → ReadyForReview → … → Approved t4 PublishRequested(rev 2) rev 2: → Published, live pointer moves rev 1: → Superseded (intact, still stamped) rollback move the pointer back to rev 1. No regeneration, no restore.

Between t0 and t4 — which may be days — every learner is reading a revision that is complete, approved, and not being touched. The cascade still fires, the approvals are still withdrawn honestly, the repair loop still runs; all of it just happens somewhere nobody is looking.

Section 7

Guards

policy_allows(action, role, state) guardrail_clean(artifact) feasible(brief) — Z3 sat grounded(node) no_permission_leak(course) all_nodes_approved(course) no_stale_nodes(course) retry_budget_left(node) versions_current(artifact) idempotency_key_unused(operation) objectives_covered(course) is_draft_revision(course) — nothing published may be edited differs_from_live(revision) — an unchanged fork is not publishable

These are the core thirteen; the transitions page lists all thirty-two, each with what it produces when it refuses. Each guard belongs to exactly one owner — OPA for permission and policy, Z3 for arithmetic and satisfiability, Datalog for grounding, dependencies, and leaks, Prolog for coverage and explanation, and the state store itself for the bookkeeping guards: retry budgets, idempotency keys, version currency, and which revision is a draft. No guard is evaluated twice by two different tools.

Section 8

Temporal invariants over the trace

These hold across the whole life of a course — including sessions separated by days.

The first line used to read G(content_generated(N) → O outline_approved), and the change is worth explaining rather than hiding. O means “happened at some point in the past”, so once a skeleton had been approved once, the premise stayed true forever. That was harmless while a skeleton could only be approved once — and became toothless the moment OutlineRevised allowed a second approval cycle, since a node could then be generated against a skeleton that was mid-revision and the formula would still hold. Naming the state instead of the history says what was always meant.

G(content_generated(N) → course_state = ContentInProgress) G(exam_generated(E) → O content_approved(topics(E))) G(published(C) → all_nodes_approved(C) ∧ ¬∃ stale(C)) G(node_edited(N) → X needs_revalidation(N)) G(generated(A) → O guardrail_checked(A)) ← new in v2 G(published(C) → policy_version(C) = current ∨ stale(C)) ← new in v2 G(restricted_chunk_used(N) → O permission_checked(N)) G(action → F audit(action)) G(published(R) → G ¬node_edited(R)) ← immutability G(live(C) = R → published(R)) G(superseded(R) → O ∃R' (successor(R', R) ∧ published(R'))) G(rolled_back_to(R) → O re_verified(R)) ← no bypass

The first of the four new lines is the immutability decision written formally, and it is the strongest statement on this page: once a revision is published, no node in it is ever edited again — at any point in the future. The nested G is what carries that “ever”. It is also cheap to check, because a single NodeEdited event against a published revision falsifies it. The last line closes the one door through which unre-approved content could otherwise reach an audience: you may return to an old revision, but never without re-verifying it first.

Section 9

What each artifact carries

Every course and every node persists more than its state name:

  • state — where it is in its machine;
  • policy_version, guardrail_version, catalog_version — what it was judged against;
  • model_id + version — who generated it;
  • kb_snapshot — which knowledge it was grounded in;
  • idempotency_key of the last side-effecting operation;
  • trace_id — the thread that ties every event together across sessions;
  • approvals[] — who approved what, when, and what they were shown at the time;
  • threshold_set — which numbers its budgets and windows came from;
  • outline_version — which committed skeleton the nodes were built against;
  • revision and forked_from — which edition this is, and which one it was copied out of.

Those fields are what make two things possible at once: resuming an editor's session three days later, and answering "which approved courses does this new rule affect?" without stopping the system.

Section 10

Open questions in this draft

  1. Where does a node removed from the skeleton go? OutlineRevised makes dropping a node a real move — it is the recovery for a node blocked on policy — but the node machine has no state for “was in this course and no longer is”. Retaining its history without leaving it in a state that reads as live wants either a state or an explicit statement that removed nodes leave the machine entirely.
  2. Is the expiry of a reader's window a state change? When the last window on a superseded revision closes, the revision stops being swept — but nothing in the model marks the moment. Either the sweep re-derives “has readers” every time, or expiry is an event and there is a state past Superseded that says so.
