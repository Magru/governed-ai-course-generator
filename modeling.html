System model

The other seven documents say what this system is and what must hold in it. This one reads them back as a model — the system reduced to the artifacts that let a stranger check it before a line of it is built, with each artifact marked present, partial or absent.

A specification is not a model. A specification states what must hold. A model is a deliberately partial abstraction with defined semantics, built to answer one question — about structure, behaviour, time, resources, failure, or whether the system can meet its goals at all. Almost everything in this set was written as specification. Reading it back as a model is what exposed the six artifacts below that had never been written at all.

The files themselves

Nine of the twenty artifacts graded below are no longer prose on this site. They are files in the model package, each answering one question, naming an owner, and naming the event that should make someone revise it — which is what this framework means by an artifact.

system-definition · functional-model · state-inventory · transitions · event-catalog · failure-scenarios · invariants · diagrams

Four of them are generated by a script that reads the tables on these pages, asserts every expected row count, and writes nothing at all if one has moved — so the trigger in each file's header is a command rather than a promise. Moving those tables into files also surfaced five questions the prose had been absorbing, none of which is answered yet.

Section 1

Five words held apart

These five get used as synonyms and are not. Keeping them apart is what makes it possible to say honestly which parts of this project exist and which are still prose about parts that do not.

TermWhat it isWhere ours stands
Specification What must hold — requirements and constraints, stated so they can be checked The seven documents in this set. This is the mature part
Architecture The structure of decisions and principles — what was chosen, and why Present but scattered: the reasoning is inline on every page, never collected
Model An abstraction of the system, partial on purpose, fitted to a specific question This page as the map, and the model package as the six artifacts that exist so far
Simulation Running possible behaviour under stated assumptions — not a proof Not built. The walkthrough is a trace executed by hand, on paper
Implementation The system that actually runs Not built. §15 describes what it will run and what it will stub — written in the present tense, which is worth correcting before the defence

The gap the last two rows describe is not a formality. A simulation that survives a thousand scenarios is not evidence that no dangerous scenario exists, and a specification that reads well is not evidence that the system it describes can meet its deadlines. Everything on this page above the line “absent” is an argument; everything below it is still a promise.

Section 2

The journey, in six parts

A vague business request becomes a checkable model in six moves, each one standing on the one before it. The framework's own contents page names eight stations; the lecture delivers six, because interface contracts and system composition are taught inside part III rather than as parts of their own. The numbering below follows the six as delivered — worth saying, because composition is where emergent behaviour comes from, and section 5 leans on that idea without a part of its own to point at.

PartThe question it settlesWhere this system stands
I · Point of departure Why an excellent AI model does not give you an excellent AI system present This is the governing principle of the whole set — the model proposes, the architecture decides, the editor leads. §3–§4
II · Defining the system Boundary, actors, authority, context, and what the system promises present Boundary, actors and external systems, drawn — the model provider sits outside it and reaches only the schema validator. context-diagram. A deployment view is still absent.
III · State, events, interaction What is permitted in each state, what the events mean, how traces behave present The strongest part by a distance: 21 + 12 states, 55 + 22 transitions, 37 guards, 31 named events. States, Transitions
IV · Time, capacity, failure Can this path meet its deadline, where is the bottleneck, how do we fail safely present All three: a 14-mode failure matrix (Safety §10), and a latency budget with a capacity model — governance costs 3.2% of the path, one model worker carries about eight editors. latency-budget
V · Simulation and verification What happens under stress, and does the model match the system partial One happy path traced by hand over 24 steps. Nothing executable, nothing stressed. Walkthrough
VI · From model to production How we learn that an assumption has quietly stopped being true partial Change-impact is modelled in unusual depth — the staleness cascade. Monitoring is not modelled at all. Cascade

The shape of the gap is consistent. Everything about logic — who may act, in what order, under which rule — is modelled thoroughly. Everything about quantity — how long, how many, how fast — is barely modelled at all. Configuration carries thresholds and budgets, and safety carries a failure matrix, but nothing anywhere states a time this system must meet or a rate it must sustain. That matters more than it sounds: if a pipeline is slow enough to exhaust an editor's patience, approvals become a formality, and every guard on this site keeps passing while the governance it exists to enforce quietly stops happening.

Section 3

The model package — twenty artifacts

A complete system model is twenty artifacts in four groups. Each answers one specific question, each has an owner, and each is updated when the evidence behind it changes — a living asset, not documentation written after the design is done. Below, every one of the twenty is matched against what this project actually has.

How to read the marks

Present means the question is answered somewhere in this set and is now kept as a file. The framework asks for artifacts, not chapters: one file per question, with an owner and an event that should make someone revise it. Nine of the twenty exist that way today, in the model package — two of them exported from the tables on these pages by a script that refuses to run when a table has moved, and two more checked against those tables by the same script. The remaining eleven are prose or nothing.

Moving those tables into files was not a formatting exercise. It surfaced five questions the prose had been absorbing — a state name that means two different things in the two machines, seven transition endpoints that are not state names, a transition that never says where the node goes, a separator that means either in one row and of in the next, an event catalog with no payloads, and — found once the linter learned to check one machine at a time — two node transitions that reach a state the node machine neither declares nor leaves. All six are written down in the package README and none of them is answered yet.

The framework is also inconsistent with itself about the size of the package — one slide calls it fourteen artifacts, the enumeration and the closing summary both say twenty. Twenty is followed here because it is the only figure that comes with a list.

Nine present, eight partial, three absent — and every one of the nine is a file. What remains absent is the production-ready half and nothing else: a deployment view for a system with no deployment, an executable simulation, and a traceability linter. The earlier version of this page said the project had been reasoned about carefully and measured not at all. The second half of that is no longer true, and the measuring changed the argument rather than decorating it — see part IV above.

Section 4

Minimum viable model

A model does not need every file in that package. It needs the minimum that lets a decision be taken without hiding a critical assumption. The left column is that minimum; the right is what a production-ready package adds on top. Marked against this system as it stands.

Minimum viable package
  • haveA measurable business outcome, in one sentence
  • haveThe system of interest, defined
  • haveBoundary, actors, external systems — drawn
  • haveDecision authority and execution authority, held apart
  • haveHard constraints
  • haveSafe fallbacks
  • haveCritical state variables, each with an owner
  • haveCritical events, each with a producer
  • haveA happy path and at least one critical failure path
  • haveAssumptions made explicit
Production-ready adds
  • noAll views consistent with one another
  • partialTraceable identifiers and versions
  • noAssumptions linked to actual measurements
  • noFailures tested rather than described
  • noA calibrated simulation
  • partialA monitoring map — signals named per assumption, none wired
  • haveChange-impact analysis defined
  • partialArchitecture decisions documented as records

Ten of ten on the left; on the right, one done and three begun of eight. The minimum viable model is complete: the framework says a model need not contain every file, only the minimum that lets a decision be taken without hiding a critical assumption, and that line is now crossed. What is missing is the production half, which mostly waits on a system that runs. The one production item already in hand — change-impact — is here in more depth than the checklist asks, because the staleness cascade is a change-impact analysis written as a state machine; nothing executes it yet, which is what the simulation is for.

Section 5

The three that get built next

Eleven artifacts are absent or partial and they will not all be written. Three are worth building before the defence. The latency budget used to head this list and now exists; what replaced it at the top is the defect that building it uncovered.

1 · A node machine that cannot get stuck done

Exporting the transition table into a file found a node state with no way out: two node transitions sent work to ErrorRecovery — a timeout while drafting, an unreachable guardrail — and ErrorRecovery is a revision state the node machine neither declared nor left. On a site whose entire thesis is that a system should not slide into a state it cannot get out of, that was the finding that mattered most, and a month of prose across four rounds of review never surfaced it.

Fixed on 2 September. The node machine has its own NodeRecovery; recovery_from records which stage failed so recovery returns the node there instead of regenerating work that was already sound; and three exits cover every branch — back to generation, back to the guardrail, or held for a person once the retry budget is spent. The node machine is now 12 states and 22 transitions. Seven endpoints in the same table are still expressions rather than state names, and each needs a resolution rule before anything can simulate this machine.

2 · The assumption list, and the monitoring map over it

Because every guard on this site rests on an assumption, and the assumptions are currently spread across six pages instead of held in one place where they can be counted. That the catalog version stamped on a block is the one the platform still serves. That the policy bundle in force is the one the revision was verified against. That the model routing table is honoured by the gateway rather than quietly overridden. Each is checked at the moment of the transition and never again. The framework's chain is assumption → runtime signal → observation → decision → model update, and this project has neither end of it: the list now exists and not one row on it is watched. The seven production signals the specification already names are the right raw material, and they measure activity rather than whether a premise still holds. Wiring them is design work and does not wait on a deployment.

3 · The executable simulation

Because the staleness cascade is the one part of this system whose behaviour genuinely cannot be predicted by reading it. A single catalog version bump touches every node that cites the changed block, each of which re-enters verification, some of which invalidate an exam that depends on their topics, which invalidates the whole-course check. How many nodes that is, how long it takes, and whether it converges before an editor gives up are questions the transition table poses and cannot answer. Emergent behaviour is exactly what a simulation exists to find.

Where these land

The first two belong on Evaluation & red team, card 08, still unwritten. The third belongs with the prototype. Nothing on this page is a reason to change the seven documents that exist — it is a reason to finish the two that do not.

Section 6

Open questions

  1. Is this page a view, or a document? It currently claims to be a map: everything on it points somewhere else, and nothing is stated here that is not stated in full elsewhere. The moment the latency budget lands, that stops being true — a summary of numbers that exist nowhere else makes this the authority on those numbers, and two places will drift. Either the budget lands on Evaluation and this page links it, or this page absorbs it and stops being a map. It cannot be both.
  2. Which of the three absent artifacts are honestly out of scope? A deployment model is the right thing for a system with a deployment, and this one has none. A traceability linter has no such excuse — an earlier draft of this page claimed there was no repository, which was simply false: these pages are a git repository, and a working model_lint.py already exists from a course assignment. That artifact is debt, not scope.
  3. Now that the assumptions are in one list, which copy is authoritative? They were distributed across six “Open questions” sections, each beside the decision it qualifies — where a reader wants them and an auditor does not. They are now also in assumptions.yaml, which is where the signals and thresholds live. Two copies of a risk picture disagree within a month unless one of them is declared the source; that declaration has not been made.
