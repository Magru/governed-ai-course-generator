Validation layers

Which engine owns which question, the rules written out in the language that actually runs them, and — the part that matters most — what each layer hands back when it says no.

A layer that returns false is a layer that has failed. Every refusal here produces an artifact: an unsat core, a leak path, a proof tree, a named rule. That is what a person acts on, what the repair loop feeds back into the next prompt, and what an auditor reads six months later. The verdict is the cheap part.

Section 1

How the questions divide

Five formal engines plus a schema validator, and the split is not by taste. Each answers a kind of question the others answer badly or not at all — and, just as important, each is bad at something the next one is good at. Naming both halves is what keeps a layer from quietly growing into a general-purpose rule engine.

LayerAnswersCannot answerRefuses with
JSON Schema Is this the right shape? Anything about meaning, relations or quantity The failing path and the expected type
OPA · Rego Is this actor allowed to do this, here, now? Whether it is possible — policy has no arithmetic The rule that denied, by name, with a message
Z3 Can these requirements hold together at all? Who is allowed to ask — it has no notion of an actor An unsat core: the minimal set that cannot coexist
Datalog What reaches what, through how many hops? Anything needing negation-as-search or arithmetic The derivation path — the chain of facts that produced the answer
Prolog What is missing, and why? Scale — it is asked narrow questions, never swept over everything A proof tree, readable as prose
Temporal logic Did this happen in a legal order? Anything about the present — it only reads history The violated formula and the event that broke it

One owner per question. No check is computed by two engines, and no engine is asked something outside its column. When two layers could answer, the cheaper one owns it — which is why “is this brief satisfiable” is Z3 rather than a Prolog search, and “may this editor author here” is OPA rather than a Datalog reachability query.

Section 2

Schema

shape · runs first · costs nothing

The least interesting layer and the one that catches the most. Every artifact the model produces is forced through a schema at generation time — the model returns a structure because it was given a tool signature, not because it was asked nicely — and validated again on the way in.

Block schema, resolved from the catalog at the stamped version
{ "$id": "catalog://schemas/image@3", "type": "object", "required": ["type", "src", "alt", "caption", "cites"], "properties": { "type": { "const": "image" }, "src": { "type": "string", "format": "uri" }, "alt": { "type": "string", "minLength": 1 }, "caption": { "type": "string" }, "cites": { "type": "array", "items": { "type": "string" }, "minItems": 1 } }, "additionalProperties": false }

Two details carry weight. additionalProperties: false means a block the catalog does not know about cannot be smuggled in as an extra field. And cites is in required as well as carrying minItems: 1 — both are needed, because a keyword like minItems only constrains a property that is present. Omit either half and a block with no source validates cleanly. With both, the schema itself requires provenance: a block with no source is malformed before anyone asks whether its claims are true.

Section 3

OPA

permission and policy · Rego · the only terminal refusal

Policy answers questions about authority: who may act, over which audience, with which sources, in which state. It is the only layer whose refusal is terminal, and the reason is worth being precise about — a constraint violation means the system produced something wrong and can try again; a policy violation means the organization has said no, and trying again is not a response to that.

Rego · authoring policy
package course.policy # rego.v1 brings in if / contains / every / in as keywords. Without it # this file parses only on OPA ≥ 1.0 and fails on anything older. import rego.v1 default allow := false # The action is permitted only if every clause below holds. allow if { input.action in {"submit_brief", "generate_outline", "generate_node"} input.actor.role == "editor" audience_permitted within_limits state_permits } # An editor may only author for audiences they were granted. audience_permitted if { every team in input.brief.audience { team in data.org.grants[input.actor.id].may_author_for } } # Thresholds come from organizational configuration, never from here. within_limits if { input.brief.node_count <= data.org.thresholds.max_nodes_per_course } # The state machine's legality, restated where policy can see it. state_permits if { input.action != "generate_node" } state_permits if { input.action == "generate_node" input.course.state == "ContentInProgress" } # Refusals are named, so the trace records which rule spoke. deny contains reason if { not audience_permitted reason := { "rule": "audience_permitted", "message": sprintf("%v is not granted authoring for %v", [input.actor.id, input.brief.audience]), } } deny contains reason if { not state_permits reason := { "rule": "state_permits", "message": sprintf("%v is not legal while the course is in %v", [input.action, input.course.state]), } } deny contains reason if { input.brief.node_count > data.org.thresholds.max_nodes_per_course reason := { "rule": "within_limits", "message": sprintf("%v nodes requested, limit is %v", [input.brief.node_count, data.org.thresholds.max_nodes_per_course]), } }

Every clause of allow has a matching deny rule, and that pairing is not decoration: allow alone would refuse with silence. A policy engine that can only say no is as useless here as a solver that can only say unsat.

Three things this file is deliberately not doing. It does not contain a list of forbidden topics — that is meaning, and it is configured elsewhere. It does not compute whether the brief is achievable — that is Z3's column. And it does not hold thresholds, only reads them: data.org.thresholds is the same object the configuration page describes, so tuning a limit never touches this policy.

Section 4

Z3

satisfiability and arithmetic · runs before money is spent

The solver answers one shape of question: can all of this be true at once? Its value is almost entirely in the failure case, because unsat on its own is useless — what the editor needs is which requirements cannot coexist.

Z3 · brief feasibility, with tracked assertions so a core exists
from z3 import Int, Solver, unsat, Bool lessons = Int("lessons") per_lesson = Int("minutes_per_lesson") total = Int("total_minutes") s = Solver() s.set(unsat_core=True) # Arithmetic itself is not a requirement anyone stated, so it goes in # untracked — it is the law that makes the others conflict, not one of # the conflicting things. s.add(lessons * per_lesson <= total) # The stated requirements are tracked, so the core names them. s.assert_and_track(lessons == 40, Bool("brief.lesson_count")) s.assert_and_track(total == 120, Bool("brief.total_minutes")) s.assert_and_track(per_lesson == 15, Bool("org.min_minutes_per_lesson")) if s.check() == unsat: core = s.unsat_core() # [brief.lesson_count, brief.total_minutes, org.min_minutes_per_lesson]
In
{ "lessons": 40,
  "total_minutes": 120,
  "audience": ["support-team"] }

org.min_minutes_per_lesson = 15
Out — refusal
unsat

core:
  brief.lesson_count          40
  brief.total_minutes         120
  org.min_minutes_per_lesson  15

"40 lessons at a 15-minute minimum
 needs 600 minutes; the brief allows 120.
 Loosen one of these three."

The split between add and assert_and_track is the whole trick, and getting it wrong is easy: track the arithmetic too, and every unsat core necessarily contains it — because the three equalities alone are perfectly satisfiable, so no conflicting subset can leave the arithmetic out. The core would then name four things, one of which is not a requirement at all but the reason the other three cannot coexist. Untracked, it becomes the law rather than a suspect, and the core names exactly the three statements a person could actually change.

Note what is in that three — org.min_minutes_per_lesson is not something the author wrote. The refusal correctly points at an organizational threshold as one of the conflicting requirements, rather than blaming the author for tripping over a setting they cannot see.

Z3 is asked the same shape of question in three other places: whether exam points sum to the stated maximum, whether a node's durations fit its lesson, and whether a proposed skeleton's counts are consistent with the brief that produced it.

Section 5

Datalog

relations, provenance, reachability · the staleness cascade lives here

Everything in this system that is a path rather than a property belongs to Datalog: does a claim reach a source, does a source reach an audience it should not, does an edit reach a node three hops away. The facts are mirrored from the platform and never re-derived — the permission predicate is the platform's, this layer only asks it new questions.

Datalog · facts (mirrored) and the three rules that matter
% ---- fact signatures, for reading. These are NOT loaded: a clause % ---- like visible_to(Article, Team). is a fact matching everything, % ---- which would make the negation below vacuously false and hide % ---- every leak. Real facts arrive from the platform and the run. % % node_cites(Node, Chunk) chunk_in(Chunk, Article) % visible_to(Article, Team) audience_of(Course, Team) % contains(Course, Node) edited(Node) % depends_on(Node, Other) % exam→topic, image→topic, prereq→node % ---- 1. a leak is a path, and the path is the refusal ---- leak(Node, Article, Team) :- contains(Course, Node), node_cites(Node, Chunk), chunk_in(Chunk, Article), audience_of(Course, Team), not visible_to(Article, Team). % ---- 2. grounding: a claim with no source ---- ungrounded(Node, Claim) :- claim_in(Node, Claim), not claim_cites(Claim, _). % ---- 3. staleness, transitively — nobody wrote the cascade ---- stale(Node) :- depends_on(Node, Other), edited(Other). stale(Node) :- depends_on(Node, Other), stale(Other).
In
node_cites(t2, ch_41).
chunk_in(ch_41, art_incident_postmortem).
visible_to(art_incident_postmortem,
           security_team).
audience_of(c_17, support_team).
contains(c_17, t2).

?- leak(t2, A, T).
Out — refusal
leak(t2, art_incident_postmortem,
     support_team).

"Node T2 cites chunk ch_41, which lives in
 'Incident Post-Mortem'. That article is
 visible to security-team. This course is
 for support-team.

 The source is excluded from T2's retrieval
 on retry."

The third rule is the one worth staring at. Nobody wrote the staleness cascade — it is two clauses, and the transitive case is one of them. The exam is stale because it depends on the topic; an illustration derived from that exam would be stale because it depends on the exam. The same two lines that make a one-hop dependency work make a five-hop one work, and no code anywhere enumerates the kinds of dependency.

Section 6

Prolog

coverage and explanation · the layer that answers “why”

Datalog says what reaches what. Prolog is asked the harder question: what is missing, and can you say why in a form a person can read. It runs on narrow questions — one course, one objective — never as a sweep.

Prolog · objective coverage, and the same predicate asked for a reason
% A node covers an objective only once a person has approved it — % teaching it is not the same as it counting. covers(Node, Objective) :- approved(Node), teaches(Node, Skill), develops(Skill, Objective). uncovered(Course, Objective) :- requires(Course, Objective), \+ ( contains(Course, Node), covers(Node, Objective) ). % The explanation is not a second implementation — it is the % same search, asked to keep what it found on the way. why_uncovered(Course, Objective, Explanation) :- uncovered(Course, Objective), findall(S, develops(S, Objective), Skills), findall(N-S, ( contains(Course, N), teaches(N, S), member(S, Skills) ), Partial), ( Partial == [] -> Explanation = no_node_teaches_any_of(Skills) ; Explanation = taught_but_not_approved(Partial) ).
In
requires(c_17, obj_escalate_correctly).
develops(sk_escalation, obj_escalate_correctly).
develops(sk_severity, obj_escalate_correctly).
contains(c_17, t1).
teaches(t1, sk_severity).
% t1 is not approved — no approved(t1) fact

?- why_uncovered(c_17, obj_escalate_correctly, E).
Out — refusal, and a next action
E = taught_but_not_approved([t1-sk_severity]).

"'Escalate correctly' is not covered.
 Two skills develop it: escalation, severity.
 T1 teaches severity but is not approved yet;
 nothing teaches escalation at all.

 Next: approve T1, and add a node for
 escalation — or drop the objective."

The first goal of covers/2 is doing real work here. Without approved(Node) the objective would count as covered the moment a node merely mentioned the right skill, and the whole predicate would answer a question nobody asked — coverage by draft rather than coverage by course. It is also what makes the two explanations different: “taught but not approved” and “nothing teaches this at all” need different actions from the editor.

This is where the editor's next best action comes from, and it is worth naming what it is not: the suggestion is derived from the uncovered set, not produced by a model. The system never guesses what the editor should do — it computes what is missing and says so.

Section 7

Temporal logic

the trace · the only layer that reads history

Every other layer looks at the present. This one replays the recorded trace and asks whether the system got here legally — because a course can be in a perfect state and have reached it through a path that should have been impossible.

Checked over the trace at WholeCourseChecks · see the full list
G(content_generated(N) → course_state = ContentInProgress) G(exam_generated(E) → O content_approved(topics(E))) G(generated(A) → O guardrail_checked(A)) G(published(R) → G ¬node_edited(R)) G(rolled_back_to(R) → O re_verified(R)) G(restricted_chunk_used(N) → O permission_checked(N)) G(action → F audit(action))

No model checker is needed for these. The trace is a finite, ordered list of events with the state before and after each, so every formula above reduces to a pass over that list — G is “holds at every index”, O is “appears at some earlier index”, F is “appears at some later one”. The checker is a few hundred lines and its output is the interesting part:

In — a trace fragment
i=41 OutlineRevised     course: CIP→OutlineChecks
i=42 NodeGenerated(t3)  node:  ContentDrafting→Generated
i=43 GuardrailVerdict   node:  →NodeChecks
Out — refusal
VIOLATED at i=42
  G(content_generated(N) →
    course_state = ContentInProgress)

  course_state at i=42 was OutlineChecks.

"A node was generated while the skeleton
 was being revised. This trace could not
 have been produced by the current
 transition table."

That last line is the point of the layer. A temporal violation is not usually a content problem — it is evidence that the implementation and the specification have drifted apart, which is exactly the failure no amount of content review would ever surface.

Section 8

The guardrail, which is not one of these

The managed guardrail sits in the same pipeline and is deliberately not a formal layer. It answers questions about meaning — is this text asking for something forbidden, in other words; is there personal data here; what is in this image — and those questions have no proof and no core. It returns a judgment.

Its verdict enters as a fact, not as a decision. The guardrail never causes a transition by itself: it produces GuardrailVerdict(allow|deny, category), and the transition table consumes that alongside the formal layers' proofs. The distinction is not pedantry — it is what keeps a probabilistic judgment from ever being the sole reason something reached a learner, and what makes “the guardrail was down” a different event from “the guardrail said no”.

Because it is configured rather than coded, it is also the only layer whose rules are not in this document. That is the point of the configuration page: a forbidden topic is a definition a compliance officer writes, not a clause anyone deploys.

Section 9

What a refusal is made of

Collected in one place, because this is the property that distinguishes the design. Each artifact has three consumers, and they want different things from it: a person needs to act, the repair loop needs to feed it into the next prompt, and the audit needs it to still mean something in a year.

LayerArtifactWhat the repair loop does with it
SchemaFailing path, expected typeRegenerates with the path named in the prompt
OPARule name and messageNothing — a policy refusal is terminal and the loop does not run
Z3Unsat core — the minimal conflicting setDoes not retry; hands the core to the editor, because no regeneration can satisfy contradictory requirements
DatalogThe derivation path: node → chunk → article → audienceExcludes the offending source from that node's retrieval and regenerates
PrologProof tree, rendered as prosePuts the uncovered objectives into the next prompt as explicit requirements
TemporalViolated formula, offending event indexNever repairs — a temporal violation is a bug report about the system, not about the content
GuardrailCategory, never the matched textRegenerates with the category named, never with the phrase — quoting it back would teach the model to reproduce it

Two rows are worth reading twice. Z3 does not trigger a retry, even though its failure is technically recoverable — because regenerating cannot make forty lessons fit in two hours, and a loop that tries is a loop that burns budget to reach the same answer. And the guardrail refuses with a category, not a quote: handing the model the exact phrase that tripped the filter is how a repair loop teaches itself to write the thing it was refused for.

Section 10

Order, cost, and an unavailable layer

The order is not arbitrary and it is not primarily about correctness — it is about what a refusal costs.

schema microseconds · no network, no state OPA milliseconds · local bundle, no model Z3 milliseconds · before generation, and again on node arithmetic ───────────────────────────── the model is called here guardrail ~100 ms · network hop, own state in the machine Datalog milliseconds · over facts already in memory Prolog milliseconds · narrow queries only temporal once per course · replays the trace at review time

Everything above the line runs before a single token is generated, which is why a malformed brief, a forbidden one and an infeasible one all cost nothing. Everything below runs against something that already exists, so its cost is bounded by what was already spent.

When a layer is unavailable

The formal engines are in-process and deterministic: if one cannot run, the deployment is broken, and the honest response is to stop admitting work rather than to admit it unchecked. The guardrail is a network hop, and its unavailability is a timeout — an unknown, routed to ErrorRecovery, not a denial. The distinction is recorded in the trace, because “we could not check” and “we checked and refused” are different facts about a course and an auditor will want to tell them apart.

No layer's absence is ever read as permission. There is no configuration value, no degraded mode and no timeout branch that turns a missing verdict into a pass.

Section 11

Open questions

  1. Who owns the fact mirror, and how fresh is it? Datalog runs over facts copied from the platform — permissions, skills, the dependency graph. A permission revoked a minute ago and not yet mirrored means a leak check that passes on stale truth. Either the mirror is transactional with the source, or the staleness of the mirror itself becomes a stamped version like every other.
  2. Is a Prolog explanation stable enough to store? The proof tree is written into the audit as the reason a node was refused. But it is derived from a rule set that can change, so replaying the same query a year later against a newer bundle may produce a different explanation for the same historical decision. Storing the rendered text solves it and freezes prose; storing the query re-derives it and may lie.
  3. How much of the temporal check can run continuously? Today the invariants are verified once, at WholeCourseChecks. Several of them — the immutability one especially — could be evaluated incrementally on every event, turning a review-time audit into a runtime assertion. That is strictly better and strictly more expensive, and nothing here has measured which invariants are worth it.
