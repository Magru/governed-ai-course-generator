Governed AI Course Generator

The model proposes. The architecture decides. The editor drives.

  • The problem. On an enterprise learning platform a course takes days to author by hand. A model could draft it in minutes.
  • The users. Course authors and training administrators.
  • The risk. One wrong action reaches an entire workforce.
  • An author's prompt asks for something the organisation forbids.
  • Restricted documents reach an audience without rights to them.
  • A lesson contradicts what was already approved.
  • A published course goes stale when a policy changes, and nobody notices.

3 · State machine

A revision moves only along the table

AwaitingBrief→BriefValidation→BriefFeasibility→OutlineDrafting→OutlineChecks→OutlineReview
↳ContentInProgress→ReadyForReview→WholeCourseChecks→PendingApproval→Approved→Published
when something failsBlockedRecoverableErrorRecoveryBlockedFinal after publicationStaleReviewWithdrawnSupersededArchived
  • 21 revision states and 12 node states, loaded from the published specification rather than written into the code.
  • Start: AwaitingBrief. Ends: Archived, BlockedFinal.
  • Failure: BlockedRecoverable, ErrorRecovery, and repair loops with a budget of two.
  • A person decides at OutlineReview, at PendingApproval and on every node.
  • Published is immutable: changing it means starting a new revision. A rule change sends it to StaleReview, where it is re-verified and never rewritten.

5 · Temporal logic

What must always hold, over the whole trace

formulain words
I2G(exam_generated(E) → Y content_approved(topics(E)))An exam is written only after its material is approved.
I3G(published(C) → all_nodes_approved(C) ∧ ¬∃ stale(C))Nothing stale and nothing unapproved is ever published.
I6G(generated(A) → O guardrail_checked(A))Every generated artifact has been screened.
I9G(action → F audit(action))Every action eventually reaches the audit trail.
I10G(published(R) → G ¬node_edited(R))A published revision is never edited, only succeeded.
I13G(rolled_back_to(R) → O re_verified(R))A rollback goes only to something re-verified.

Fifteen invariants are checked over every run, and each one has a test that breaks a working run by a single field to prove it can fail. G = always · F = eventually · O = once in the past · Y = in the previous step.

6 · Neuro-symbolic architecture

The neural parts propose and read; the symbolic parts decide

Neural

  • Gemini writes the outline and each node, in the positions it is given: rules, the author's text and the sources, kept apart.
  • Bedrock Guardrails reads for meaning: denied topics, personal data and content filters, at every point where text enters or leaves.

Symbolic

  • The state machine decides which move is legal.
  • OPA, Z3, Datalog, Prolog, JSON Schema answer the guards.
  • Temporal logic checks the whole trace.
  • Who decides: the transition table. A model's answer is an event the machine judges, never an instruction it follows.
  • On a conflict, any refusal wins. In the live run the guardrail allowed every artifact, and the symbolic layers still refused five of them.
  • The last word belongs to a person. Nothing neural can approve.

11 · Production readiness & roadmap

What works, what is still a demo, what comes next

Works

  • The machine runs from the published specification, and the build fails if the two drift apart.
  • Six engines, a gateway with eleven stages, and idempotency keys.
  • Live: Gemini writes, Bedrock Guardrails screens, and one node was written, screened and checked.
  • Rollback: re-verify, then move the pointer. Versioning: every node is stamped with the policy, guardrail, catalog and knowledge-base versions it was checked under.

Still a demo

  • The evidence rests on a recording. One live course has reached publication, once; a model answers differently every run.
  • There is no image provider and no Bedrock generator.
  • There is no monitoring: of eleven assumptions, none has a signal yet.

Next

  • A monitoring map over the assumptions
  • An adapter to the platform's real API
  • Guardrail versions in the admin panel
  • A load simulation, then deployment

The question

How does the system keep an AI agent from drifting, over time, from a correct sequence into a dangerous or forbidden one?

  1. State: the forbidden sequence has no row in the table, so it cannot be taken. A refused event moves nothing and is recorded.
  2. Events: the agent acts only through registered actions, and each one is a question to a guard before anything is spent.
  3. Guards: OPA, Z3, Datalog and Prolog each refuse their own kind of fault, with a reason the next attempt is given.
  4. Time: temporal logic checks the whole trace, so drift across steps is caught, not just a bad step.
  5. Change: a new policy, guardrail, catalog or knowledge base re-verifies what it reaches. An approval does not outlive the rules it was given under.
  6. People: the model proposes, and only a person approves.
